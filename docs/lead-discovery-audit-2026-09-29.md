# Arcli lead-discovery reliability audit — 29 September 2026

**30 September follow-up:** The Free onboarding, dashboard, pricing, and landing page now describe a website-based matching brief rather than claiming a Free public scan or live match count. Paid empty queues distinguish pending verification, failed or partial coverage, zero retrieved posts, and candidates that did not become review-ready. This corrects customer-facing claims and diagnosis; it does not add Free source ingestion, prove paid production yield, or resolve the durable worker issues ranked below.

## Verdict

**Pipeline is partially blocked.** The repository contains a real path from a public post to a tenant-owned `lead_matches` row and a paid dashboard query. Five public-source adapters returned normalized posts in a small live probe. This establishes technical possibility, **not** a production success rate or a useful-lead guarantee. The current Free experience cannot generate its advertised preview count through the ordinary activation path. Paid discovery has several paths that can acknowledge work or finish a scan without a durable, visible lead. There is no evidence in this checkout that a real production tenant has completed the full path.

The larger product judgment is unfavorable for a broad, self-serve promise of consistent leads across arbitrary B2B categories. HN and Bluesky provide general public discussion; GitHub, Stack Exchange, and Lemmy are selected only for certain product contexts. The first pass searches a bounded 90-day window, limited queries and result pages, then ranks only a small set for verification. Even when all infrastructure works, many categories will have sparse public buyer conversations, and a relevant public author is not necessarily an identifiable, reachable buyer. A narrower, measured v1 with human review is credible; a universal lead-volume claim is not.

## Silent failure paths and observability

An HTTP 202 from crawl/embedding/public-ingestion triggers says only that a handoff was accepted. A `crawl_jobs.status='completed'` row says the website profile was persisted, not that discovery ran. `initial_public_ingestion_job_completed` in logs means jobs were submitted, not that any provider returned a post. `discovery_runs.status='completed'` can mean all *source requests* finished, while `verification_pending` is true; `partial` can simply mean the five-minute window expired. `source_posts` rows are global corpus records; they are not tenant-visible leads. `discovery_candidate` and `rejected` rows will not appear in the default ready queue. A valid ready row can be hidden by the active-profile timestamp, Free entitlement, RLS, a failed Supabase read (the dashboard logs and returns `[]`), or top-20 truncation. Watchlist/target/research rows are different products and do not imply `lead_matches`.

The existing `discovery_run_events`, candidate-pool counters, source failure details, and actor logs are useful, but optional telemetry is intentionally fail-open (`api/services/social/discovery_telemetry.py`). There is no durable per-run invariant that reconciles provider hits → admitted posts → embedding attempts → verifier decisions → committed leads → dashboard-visible rows. Add that funnel, with reason-coded drop counts and queue age, before treating a scan status as evidence of delivery. Alert on paid runs that end with plausible candidates but no committed match, and on embedding/verifier backlog older than the UI's polling window. Do not log raw post text or credentials.

## Make it real: v1 scope and phases

**Smallest viable product:** one chosen buyer segment, one or two reliable public sources, source-native ingestion with immutable IDs and permalinks, a durable candidate/verification queue, deterministic evidence checks, a human review inbox, and outcome feedback. For founder/developer tools, start with HN and narrowly selected GitHub issue discussions. HN exposes public founder questions through a searchable API; GitHub gives scoped issue context for developer tools. For other B2B segments, do not advertise coverage until a provider-specific pilot shows enough public buyer situations. Bluesky is a useful optional supplement but its search availability and relevance should be monitored per query; Stack Exchange is better treated as problem research unless source evidence shows commercial intent. Lemmy and X can wait until measured incremental yield exceeds complexity and cost. Reddit should remain off without an approved access arrangement.

Every customer-visible actionable lead should carry a valid original permalink; captured source text and exact evidence quote; source time and freshness; identifiable public author/organization **only when directly supported**; a specific problem, request, or evaluation signal; product/buyer fit; and an explicit confidence/uncertainty label. The current model should suggest a review priority, not decide purchase authority, company identity, budget, or contactability from a short post. Relax the pre-storage lexical/buyer-cue filter if real labeled cases show missed relevant posts; retain a conservative actionable gate after deterministic citation checks. Keep warm/exploratory items visible as lower-priority research signals. Do not increase the verifier threshold simply to improve apparent precision by hiding volume.

An initial human review step is necessary. Reviewers should label `actionable`, `useful research`, `wrong buyer`, `stale`, `promotion`, and `not enough evidence`, with source and reason. Use those labels to measure precision among the first N surfaced posts, useful leads per paid tenant per week, and the share of accounts receiving at least one useful item. Track source requests/model cost per useful lead and report zero-yield runs honestly. A human reviewer can improve precision immediately, but review throughput limits scale; automation should replace only rules whose error rates are measured.

**Immediate:** deploy the five code fixes and updated migration checklist in this audit; configure an explicit backend URL; add queue/contract readiness checks; show distinct `profile ready`, `sources searched`, `verification pending`, `no source coverage`, and `ready to review` states; fix the Free preview promise; pilot a small number of paid customers manually. This improves operational truth and prevents silent zeroes but cannot create conversations that sources do not contain.
